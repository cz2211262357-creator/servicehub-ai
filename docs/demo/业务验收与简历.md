# 业务验收与可说明的项目经历

## 操作流程

1. 以管理员登录，查看知识库中的售后政策是否已就绪，查看运行配置已接入在线模型。可上传自己的 Markdown/TXT/文本 PDF，等待真实 Embedding 完成。
2. 以 customer@example.com 登录，创建会话，问“签收后七天内可以退货吗，需要保留什么？”。回答应来自实际知识片段，引用下载需要当前登录身份。
3. 发送“查询订单 SH20261021001，商品无法开机，帮我准备退货申请”。Agent 只能调用已授权工具，查当前客户订单并生成草稿。确认前正式工单不存在。
4. 点击草稿的确认提交，进入售后工单查看待审核状态。重复确认使用同一幂等键，只产生一个结果。
5. 客户点击转人工；用另一浏览器/无痕窗口以 agent@example.com 登录，接单、人工回复。客户应立即收到同一条持久化消息。人工接管后迟到的 AI 不能新增正式回复。
6. 客服将工单依次改为审核中、通过、已完成，查看时间线。非法跨状态操作会返回冲突并写入审计。
7. 管理员查看真实运营聚合、任务状态与审计。换第二企业/第二客户核对订单与会话不可串读。

种子是虚构商家数据，模型接口与所有业务写入均真实执行。切勿把本地种子写成真实商业客户或生产接入经历。

## 简历可用表述

项目名称：ServiceHub AI 电商售后与知识库服务平台
技术栈：React、TypeScript、FastAPI、SQLAlchemy asyncio、MySQL、Redis、Docker Compose、百炼 Function Calling / Embedding。

- 独立实现客户门户与客服控制台，覆盖多租户认证、会话接单、订单查询、售后确认及审核、文档版本管理与敏感操作审计。
- 基于 MySQL ngram 全文检索与 Redis HNSW 实现混合召回，结合 RRF、租户过滤和有效版本复核，支持带来源引用的知识问答。
- 使用百炼在线模型编排政策查询、本人订单查询及售后草稿工具，约束工具参数、调用步数和输出预算，正式售后操作由客户明确确认。
- 通过事务 Outbox、任务租约和执行版本实现跨进程任务恢复；结合唯一幂等键、版本更新与会话代次处理重复提交、抢单和人工接管竞态。
- 编写真实 MySQL/Redis 与双 API 进程测试，实际验证 Worker 进程终止、Redis 短暂故障、消息补放和业务一致性；交付 uv 环境、Docker 部署与复现脚本。

性能数字仅可引用 docs/verification 中的具体工作负载、硬件环境和样本。不要写“百万并发”“线上提升 xx%”或把本地闭环业务接口测量解释为大模型服务容量。

## 面试中需要能讲清楚

为何数据库是权威源；Outbox 的重复投递如何与业务幂等配合；数据库租约为何要执行版本；接管后的 AI 为什么不能落库；WebSocket 如何跨进程和断线补放；Redis Search 为什么用独立 db0；文档停用如何阻止旧候选引用；工具为何不能直接退款；全局并发槽与接口限流有什么区别。
